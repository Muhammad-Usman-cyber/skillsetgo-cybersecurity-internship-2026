# Authentication & Session Weakness Analysis

## Objective
Analyze session management weaknesses in a legal practice environment (DVWA) by reviewing how session identifiers are generated at different security levels.

## Target
- **Application:** DVWA — Weak Session IDs module
- **Method:** Server-side source code review (`view_source_all.php?id=weak_id`), comparing session ID generation logic across security levels

## Finding — Predictable Session ID Generation (High Security Level)

**Evidence (source code):**
```php
if (!isset($_SESSION['last_session_id_high'])) {
    $_SESSION['last_session_id_high'] = 0;
}
$_SESSION['last_session_id_high']++;
$cookie_value = md5($_SESSION['last_session_id_high']);
setcookie("dvwaSession", $cookie_value, time()+3600, "/vulnerabilities/weak_id/", $_SERVER['HTTP_HOST'], false, false);
```

**Analysis:** Even at DVWA's "High" security setting — intended to represent the more hardened configuration — the session ID is generated by MD5-hashing a simple incrementing integer counter. There is no random component (no `random_bytes()`, no cryptographically secure token generation) anywhere in this logic.

**Why this matters:** MD5 is a fast, publicly known hash function with no secret key involved. Since the input is just "1, 2, 3, 4…", an attacker who observes even one valid session cookie can pre-compute the MD5 hash of every nearby integer and generate a list of other likely-valid session IDs — no brute-forcing of the hash itself required, just brute-forcing tiny integers.

**Comparison note:** For contrast, DVWA's "Impossible" (i.e. properly fixed) implementation uses:
```php
$cookie_value = sha1(mt_rand() . time() . "Impossible");
```
This combines a random number, the current timestamp, and a fixed string before hashing — dramatically increasing the search space an attacker would need to guess a valid value, even though it's still hash-based rather than using a proper cryptographically secure random token generator.

**OWASP mapping:** A07:2021 — Identification and Authentication Failures

**Potential impact:** If an attacker can predict or enumerate valid session IDs, they can hijack another user's session without needing their password — bypassing authentication entirely once a session is active.

**Recommended fix:**
1. Generate session identifiers using a cryptographically secure random source (e.g. `random_bytes()` in PHP), not a hash of a predictable counter.
2. Ensure session tokens have sufficient length/entropy that brute-forcing is computationally infeasible.
3. Set `HttpOnly`, `Secure`, and `SameSite` flags on session cookies (note: this implementation also passes `false, false` for the `secure` and `httponly` cookie flags, a separate weakness compounding the risk).

## Summary

| Security Level | Session ID Method | Weakness |
|-----------------|--------------------|----------|
| High | `md5(incrementing counter)` | No randomness — trivially predictable |
| Impossible (fixed) | `sha1(random + timestamp + string)` | Properly randomized |
